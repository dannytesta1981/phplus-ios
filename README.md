# phplus 1.2

Native SwiftUI iPhone app (iOS 17+) with Face ID/device passcode protection and three configurable HTTPS web spaces. No sites, credentials, analytics or personal data are included.

## Install with Feather
Import phplus-1.2-unsigned.ipa into Feather, sign with your valid certificate and provisioning profile, then install. The unsigned file cannot be installed before signing. Unlock and tap a space or its pencil to configure it.

WKWebView stores cookies and sessions on this device. Website policies can expire sessions or reject embedded-browser authentication. No certificate validation bypass is implemented. JavaScript, redirects and web dialogs are supported. User-initiated popups use the WKWebViewConfiguration supplied by WebKit, retaining opener semantics and the persistent cookie store. Up to three child windows are allowed; close them from the browser menu. Camera and microphone capture stop when a child is closed or the browser is dismantled. Authentication requiring an external app callback or a provider that rejects WKWebView is outside this release's scope.

The app covers its UI while inactive and locks on background when enabled. Face ID/device passcode starts automatically on launch and after a real background transition, without retriggering on temporary inactive states caused by iOS prompts. Only failed/cancelled attempts show manual retry. Impostazioni → Sicurezza allows changing the default-on lock; both enable and disable require successful device-owner authentication. Stale callbacks cannot unlock or change settings after background.

## Build
Install XcodeGen from Homebrew, run `xcodegen generate`, then open phplus.xcodeproj. The macos-15 GitHub workflow builds Release for physical iPhone ARM64, checks the binary and packages Payload/phplus.app as an unsigned IPA. It also exports a source ZIP containing the generated Xcode project.

Compilation and binary validation do not replace physical-device testing of Face ID or the user's configured websites.

## 1.1 camera access

The compiled Info.plist includes NSCameraUsageDescription and NSMicrophoneUsageDescription. The WKUIDelegate capture callback denies insecure/opaque origins, mismatched requester/frame origins or ports, inactive/nonvisible webviews, and iOS-denied/restricted capture. Every eligible request uses WKPermissionDecision.prompt (never unconditional grant), allowing WebKit's trusted site-specific prompt and iOS first-use authorization. No application-level cross-site grants are stored. Third-party HTTPS identity frames may request consent only when permitted by the embedding document; phplus does not relax Permissions Policy, iframe sandbox, HTTPS, TLS, or WebKit restrictions.

The browser menu includes Diagnostica and Apri in Safari. Diagnostics are bounded and in-memory only: fixed technical event codes plus frame origin host, without URL paths/queries, credentials, page text, arbitrary JS messages, device IDs, constraints, or media. It distinguishes API availability, secure context, inspectable frame camera policy, native iOS authorization status, media acquisition errors, JS runtime errors, HTTP status and popup/redirect activity. NotAllowedError is ambiguous and is explicitly labelled as such. Page-origin signals are untrusted and may be changed by the site; they never affect authorization. The getUserMedia observer forwards the original arguments, receiver, stream and rejection object, and never requests capture itself.

If the service explicitly requires Safari or rejects an embedded browser, use Apri in Safari and restart its verification there. This opens the current HTTPS URL with the system browser (Safari when configured as default). phplus cannot transfer its cookies/session to Safari; login may be needed again, and session-bound callback links may require restarting from the service's entry page. No claim is made that a specific identity provider works without testing on an iPhone.

## Validation scope

CI runs nine native Swift capture-origin policy checks plus JavaScript diagnostics/context/error/privacy regression checks, builds the physical-iPhone ARM64 Release, and verifies the actual packaged usage descriptions, diagnostics resource and media-permission delegate selector. These checks do not exercise the iPhone camera, permission dialogs, biometric liveness, identity-provider acceptance, popup callback compatibility or iframe behavior on a real site. These remain physical-device tests. Simulator/unit/VM checks must never be described as successful face scanning.

## 1.2 lifecycle and lawful persistence

Each portal owns one retained WebState, WKWebView, host view, coordinator and popup stack for the lifetime of this process. Locking adds an opaque overlay rather than removing NavigationStack or the browser. Switching portals or returning from another application does not reload the entry page. The same web history, scroll, DOM and sessionStorage remain available while WebKit keeps its content process alive. Camera/microphone capture is stopped on background/lock/navigation away; a live media stream cannot be persisted or silently resumed. No site data is removed by locking, checkpointing, portal changes or normal app closure. Changing a configured portal URL intentionally replaces that portal's in-memory browser but leaves the shared persistent web data intact.

WKWebsiteDataStore.default() owns cookies, localStorage, IndexedDB, service-worker data and other supported data according to WebKit/site rules. There is no public synchronous flush-to-disk API used here. At navigation completion/background the app records a best-effort asynchronous observation through WKHTTPCookieStore and read-only storage counts, with a finite iOS background task. It does not rewrite cookie expiration, serialize tokens or revive session cookies, sessionStorage, JS memory, live media or expired identity checks. Abrupt force-quit or content-process termination can lose volatile state or recent writes; the server can independently revoke/expire a verification. Counts decreasing can indicate local change, expiry or website action; unchanged counts do not prove token validity or that the server alone required re-verification.

User-configured portals are migrated unchanged from the 1.0/1.1 UserDefaults key into an atomic iOS complete-file-protected, backup-excluded Application Support file. The old defaults entry is removed only after a successful write. The bundle ID and persistent WebKit store remain unchanged. Do not uninstall, clear data or change the signing identity/bundle ID when installing the update if you want to retain the existing sandbox. If protected files cannot be read, the app reports that condition and does not overwrite them.

Cold restoration saves the active portal and only strictly allowed read-only HTTPS navigation paths on the configured origin. The narrow route vocabulary is defined in RestorationPolicy. Every query, fragment, userinfo, percent-encoded path, unknown path, foreign origin/port and non-GET operation is excluded. This intentionally sacrifices restoration of some harmless routes to avoid persisting opaque secrets or automatically replaying operations. Excluded transient pages invalidate the previous restoration candidate. Configured entry URLs and allowed resume records are protected files, never new navigation entries in UserDefaults. No full web history or form state is serialized. A blocked current page falls back to a safe configured entry; if the entry itself is not admitted for automatic restoration, it requires an explicit tap on Pagina iniziale. There is no generic way to prove a site's GET endpoint is side-effect-free; the allowlist is deliberately limited to common navigation routes and does not include payment or operation routes.

## 1.2 test matrix

CI uses iPhone 16 Pro / iOS 18.5 simulator with a locally trusted HTTPS fixture and synthetic non-user data. XCTest covers automatic-auth scheduling using an injected authenticator (no release bypass), duplicate suppression, authenticated settings changes and preference persistence, stale callbacks, migration, protected cold restore, sensitive route rejection, retained WKWebView identity/single load, real WKWebView history/scroll/DOM retention under lock transitions, HTTPS getUserMedia API exposure and the unchanged camera usage keys/delegate. A second separate xcodebuild test invocation verifies that a persistent secure cookie, localStorage and IndexedDB survive termination/relaunch of the test-host process. The local test certificate is trusted only inside the disposable simulator; production code has no TLS bypass.

These are simulator/injected-auth tests. They do not claim to exercise a real iPhone Face ID prompt, physical app switching under memory pressure, physical camera capture, facial liveness, provider acceptance or provider-mandated identity expiry. The user's physical-iPhone confirmation of working 1.1 camera behavior is a baseline, not proof that 1.2 physical capture has been retested. Install 1.2 as an update and verify those physical flows separately.
